Malware False Positives

AutoHotkey's executable files are occasionally flagged as malware, usually with vague labels such as "Trojan.Heur!" or "Malicious.high.ml.score", and sometimes more specific (but incorrect) labels such as "Trojan:Win32/Wacatac.H!ml". Generally no explanation or evidence is given as to why the file was classified as such, so all anyone can do is report each false positive to the appropriate vendor.

This document offers some potential explanations as to why this happens.

C Runtime Library

Up to v2.0.32, AutoHotkey executable files were built with the statically linked C runtime library. This essentially includes C runtime functions in the executable file itself in order to make the file more portable. This is Microsoft code and not indicative of any behavior or intent of the program itself. Some developers have observed a higher rate of false positives when the runtime is statically linked, including detections by Microsoft Defender.

Windows 10 and later include the "Universal CRT". Linking to this allows the program a degree of portability while potentially reducing malware false positives, and reducing the size of the files as a bonus. For older supported Windows versions, the Universal CRT can be installed by the Microsoft Visual C++ Redistributable or Windows update KB3118401.

Detection Methods

Detection based on a database of signatures only works if the signature of a file is already in the database. Security products use a number of other strategies to catch new or unknown threats, such as rule-based heuristics and machine learning.

Each new release or compiled script may have its own unique signature, making it less likely to match a signature already verified as safe, and more likely that it will be subject to error-prone heuristics or machine learning.

Automated analysis of a file cannot judge the intent of a program, only score risk based on various factors. For practical reasons, a significant weight is likely placed on the file's static content: function imports, strings, code and other indicators.

  • Imports: The function import table is a list of functions which the program imports from system components or other DLL files. Inspecting a program's function imports can give an indication of its capabilities. Function imports can be matched to known attack techniques as a method of scoring risk, although in many cases a function can have both benign and malicious potential.

  • Strings: Functions can be resolved at runtime, so analyzers also look for function names within the content of the file. If the name of a sensitive API is found within the file but not in the import table, that could indicate an attempt to evade detection. Other strings within the file might have significance, such as specific environment variable names (T1059.003), window classes or window titles (T1057).

  • Code: Code can be decompiled and analyzed by an automated process, or fed through machine learning models. This can detect patterns which aren't as simple as importing a specific function.

  • More: If the payload or code within the file can't be fully analyzed, it stands to reason that the file must be treated with caution. Analyzers flag payloads which are executable or are suspected to be compressed, encrypted or obfuscated.

MITRE ATT&CK® Indicators

MITRE ATT&CK® is a globally-accessible knowledge base of adversary tactics and techniques based on real-world observations. It is referenced by some PE analyzers and sandboxes. These tactics and techniques are likely what antivirus heuristics are designed to detect. Some indicators might be individually benign and common, but the presence of several indicators likely raises the "malware score" of a file.

In most cases, these are associated with functions which are imported for the purpose of potential use by scripts.

T1027.002 Obfuscation: Software Packing

Analyzers and sandboxes have several different ways to report that the file is packed, either generally or specifically with UPX. For v2.0.0 through v2.0.32, AutoHotkey setup is compressed with UPX.

UPX is open source and reversible. Even some free tools are able to automatically analyze the unpacked version of the file. Even so, analyzers and sandboxes report it as a risk indicator, so perhaps it also gets negative treatment by antivirus heuristics.

Testing with AutoHotkey setup files based on v2.0.32 showed the method of packing to have no obvious impact on the rate of false positives.

T1027.007 Obfuscation: Dynamic API Resolution

AutoHotkey resolves APIs at runtime, such as for DllCall or when calling certain functions which can't be directly imported for whatever reason. The capability to resolve an API at runtime can be detected, and is an indicator of risk because the program might be hiding which functions it imports.

Analyzers flag the presence of LoadLibrary and GetProcAddress. It is possible to resolve APIs without these functions, but being caught doing so would be even more suspicious, as there is likely no purpose other than to evade detection.

T1027.015 Obfuscation: Compression

Compressed payloads are standard fare for EXE-based installers such as AutoHotkey setup. The methods we use are easily reversed by existing PE analyzers, but might still contribute to risk scoring by heuristics or machine learning models in some antivirus engines. The standard interpreter binaries (such as AutoHotkey64.exe) contain only common resources, such as icons, dialogs and menus.

T1055.009 Process Injection: Proc Memory

This is raised by the presence of functions used to implement ListViewGetContent and StatusBarGetText, which require writing to a struct in the remote process.

T1056.001 Keylogging

This is raised by the presence of the following functions:

  • SetWindowsHookEx, which can install keyboard hooks and other types of hooks.
  • GetKeyboardState, which is used for more reliable changes in modifier state during ControlSend.
  • GetAsyncKeyState, which is used by GetKeyState and to determine modifier state during Send or hook hotkey recognition.

AutoHotkey installs a keyboard hook for various purposes, when needed by the script.

SetWindowsHookEx is also used for journal playback hooks; i.e. SendPlay.

The native GetKeyState function has also been associated with keylogging, but is widely used for benign purposes. The function import was not directly flagged by the analyzer, but the presence of a loop which "logs keystrokes by polling key state" was flagged. This appeared to be pointing to calls within the message loop, which check the modifier keystate and do not poll for keys.

T1057 Process Discovery

This is raised by the presence of functions used to implement ProcessExist, ProcessWait and ProcessGetParent. ProcessGetName and ProcessGetPath also rely on these functions to resolve a name to a process ID.

Some sandboxes identified that the program "may try to detect the Windows Explorer process (often used for injection)". This may have been triggered by the strings "Shell_TrayWnd" and "Program Manager". The former is used to find the taskbar for various benign purposes (check the source code for details), and the latter is used to exclude the desktop window from GroupAdd.

T1059.003 Windows Command Shell

Adversaries may leverage cmd to execute various commands and payloads.

This is raised by the presence of the variable name ComSpec and the functions used to implement Run. AutoHotkey setup's uninstall routine uses ComSpec to self-delete.

T1070.006 Timestomp

Adversaries may modify file time attributes to hide new files or changes to existing files.

This is raised by the presence of SetFileTime, which is called only when the script calls FileSetTime.

T1071.001 Web Protocols

Associated with Download.

T1095 Non-Application Layer Protocol

Socket (network) functions are used by the debugger backend to implement the DBGp protocol.

T1112 Modify Registry

Adversaries may interact with the Windows Registry as part of a variety of other techniques to aid in defense evasion, persistence, and execution.

Associated with RegWrite.

There are many legitimate reasons to write to the registry, so this probably only affects detection rate when combined with other factors, if at all.

T1113 Screen Capture

This is raised by a combination of GDI functions used by ImageSearch and PixelSearch, which technically do capture an image of the screen into a temporary buffer in order to perform the search.

T1115 Clipboard Data

Associated with A_Clipboard, ClipboardAll and OnClipboardChange.

T1134 Access Token Manipulation

Adversaries may modify access tokens to operate under a different user or system security context to perform actions and bypass access controls.

The Shutdown function requires the use of access token manipulation to get the shutdown privilege.

T1497.003 Virtualization/Sandbox Evasion: Time Based Checks

AutoHotkey's code contains timing checks via repeated tick count, such as to perform period message checks during execution of a script, or to stop waiting when a timeout has elapsed. The analyzer flagged these because timing checks can be used for anti-analysis purposes.

T1547.009 Boot or Logon Autostart Execution: Shortcut Modification

In at least one instance (but not all), a sandbox flagged the use of the ShellLink COM object by AutoHotkey setup and erroneously described it as related to autostart. The shortcut file is created in A_Programs or A_ProgramsCommon, not the Startup subfolder. This is a very common action for an installer.

This was an error in the sandbox's recognition and likely would not affect false positive rates.

T1553.003 Subvert Trust Controls: Code Signing

Setup creates a self-signed root certificate for the purpose of signing the UIA executable files for Run with UI access, which requires a signed binary. This is more likely to be detected by a sandbox than by static analysis. It poses no risk to users, but generally might look suspicious because developers of legitimate software usually choose to either sign with a paid certificate or not sign at all (i.e. when they don't need UI Access).

In future, signed releases will obviate the need for the self-signed certificate.

T1622 Debugger Evasion

Adversaries may employ various means to detect and avoid debuggers.

Two separate functions raise this:

  • OutputDebugString, which is not called directly by release builds of AutoHotkey except when the script calls OutputDebug.
  • IsDebuggerPresent, which is called by the C runtime when specific unhandled errors occur. Official builds of AutoHotkey statically link the C runtime and therefore contain this code.

Other Indicators

These risk indicators were detected by running AutoHotkey executable files through PE analyzers. These are more general indicators which weren't explicitly associated with specific MITRE ATT&CK® techniques in the analyzer's output. An indicator might be only a reason for an analyst to take a closer look at the file, but if it is of concern to security analysts, it could potentially contribute to heuristics or machine learning based detection.

Process-Launch APIs

The analyzer flagged the functions used by Run, RunWait and menu options such as for opening the help file. The capability to launch other programs is common and probably only affects detection rate when combined with other factors, if at all.

Interacts with Services

Up to v2.0.32, A_IsAdmin was implemented by querying the service control manager. This approach was likely used for compatibility with older systems. A cleaner method can be used since AutoHotkey dropped support for Windows XP and earlier.

Code Signing

Code signing does not stop false positives, but the lack of a signature is almost always shown as a risk indicator. There is anecdotal evidence that unsigned files are more likely to be flagged as malware. Current AutoHotkey releases are not signed but we are working on setting up code signing.

Signing AutoHotkey releases will not help authors of compiled scripts. As the process of compiling a script requires modifing the base executable file, the signature must be stripped from the file. Authors of compiled scripts have the option of signing compiled scripts using their own code signing certificate.
